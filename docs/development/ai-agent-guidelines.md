# AI Agent Guidelines

This document provides guidelines for AI coding agents (including Claude, GitHub Copilot, Cursor, and similar tools) working on the ZipKit repository.

## Before Making Any Changes

### 1. Read Project Documentation

**Always read** the following before implementing changes:

#### Required for All Changes

- **`.claude/README.md`** — Overview of agent operating rules
- **`.claude/PRINCIPLES.md`** — Non-negotiable engineering principles
- **`.claude/WORKFLOW.md`** — Issue-driven development process
- **`.claude/COMMITS.md`** — Commit message standards

#### Required by Task Type

| Task Type         | Read These Documents                                  |
| ----------------- | ----------------------------------------------------- |
| All PRs           | `.claude/PULL_REQUESTS.md`                            |
| Creating branches | `.claude/BRANCHES.md`                                 |
| Code changes      | `.claude/ISSUE_EXECUTION.md`, relevant `/docs/` files |
| Tests             | `.claude/TESTING.md`                                  |
| Security changes  | `.claude/SECURITY.md`, `/docs/security/`              |
| Releases          | `.claude/RELEASES.md`                                 |

### 2. Understand the Issue

Before writing code:

1. **Read the GitHub issue completely**
2. **Review linked documentation** and related issues
3. **Verify dependencies** are complete (blocking issues resolved)
4. **Ask clarifying questions** if requirements are ambiguous
5. **Never silently expand scope** — create follow-up issues for new work

### 3. Verify Your Understanding

If documentation is unclear or contradictory:

- **Do not guess** the intended behavior
- **Do not make assumptions** about architecture
- **Create an issue** to resolve the ambiguity
- **Ask the maintainer** for clarification

## Core Rules for AI Agents

### No AI Attribution

**Never include AI attribution** in any repository metadata:

❌ **Forbidden**:

- Commit messages: "Generated with Claude Code"
- Commit trailers: `Co-Authored-By: Claude <noreply@anthropic.com>`
- PR descriptions: "Created by AI"
- Code comments: "// Generated by Copilot"
- Documentation: References to AI/Claude/Anthropic
- Issue comments: "Claude suggests..."

✅ **Allowed**:

- Writing code and commits as if written by a human developer
- Following the same standards as human contributors
- Documenting the engineering reasoning, not the tool used

### Why No Attribution?

Repository history documents **engineering decisions**, not the tools used to implement them. Just as we don't add "Written in VS Code" to commits, we don't add AI attribution.

## Issue-Driven Development

### Work from GitHub Issues

1. **Find or create an issue** for the work
2. **Link your PR to the issue** using `Closes #N` or `Related to #N`
3. **Stay within issue scope** — don't silently add extra features
4. **Create follow-up issues** for new work discovered during implementation

### When to Create New Issues

Create follow-up issues when you discover:

- Additional bugs or edge cases
- Related improvements or refactoring
- Missing tests or documentation
- Architectural concerns
- Security vulnerabilities

Label the new issue appropriately and link it to the current work.

## Keep Changes Small and Focused

### One Logical Change Per Commit

✅ **Good**: Separate commits for:

```
feat: add TAR archive format detection
test: add TAR format detection test fixtures
docs: document TAR format support
```

❌ **Bad**: Single commit for:

```
feat: add TAR support, fix ZIP bug, refactor security, update deps
```

### One Focused Issue Per PR

- **Small PRs get reviewed faster** and have fewer conflicts
- **Large PRs are risky** and difficult to review
- **Break up unrelated changes** into separate PRs

When a change grows too large, consider:

1. Breaking it into multiple smaller PRs
2. Creating a tracking issue with subtasks
3. Implementing in phases with feature flags

## Testing Requirements

### Add Tests for All Changes

**Every behavioral change requires tests**:

- **New features**: Add unit, integration, and E2E tests
- **Bug fixes**: Add regression test demonstrating the fix
- **Refactoring**: Ensure existing tests still pass
- **Documentation**: Update examples and verify they work

### Test Coverage Targets

- **Security-critical code**: Aim for comprehensive coverage
- **Archive processing**: Aim for high coverage
- **UI glue code**: Coverage less critical but still required
- **Never**: Write meaningless tests just to hit coverage numbers

### Never Disable Tests to Make Changes Pass

If tests fail after your change:

✅ **Good**:

- Fix the implementation to match the test
- Update the test if requirements changed (document why)
- Add new tests for new behavior

❌ **Bad**:

- Comment out failing tests
- Use `.skip` without creating issue
- Weaken assertions to make tests pass
- Disable entire test suites

See `.claude/TESTING.md` for complete testing requirements.

## Update Documentation

### When to Update Documentation

Update docs whenever you change:

- **Public APIs**: Function signatures, return types, error conditions
- **User-facing behavior**: New features, changed workflows, removed features
- **Architecture**: Major structural changes, new patterns
- **Security model**: Permission changes, threat model updates
- **Configuration**: New options, changed defaults

### Where to Update Documentation

- **Code comments**: JSDoc for public APIs
- **README files**: For workspace-level changes
- **`docs/` directory**: For significant features or architecture
- **`.claude/` directory**: For process or workflow changes (requires approval)

### Keep Documentation Accurate

- **Never describe unimplemented features** as complete
- **Remove documentation** for deleted features
- **Update examples** to match current API
- **Test documentation code samples** to ensure they work

## Change Review Process

### Before Pushing

Run all checks locally:

```bash
npm run format
npm run lint
npm run typecheck
npm run test
npm run build
```

All must pass before pushing.

### When Opening a PR

1. **Use descriptive title** following Conventional Commits format
2. **Provide context** in PR description (don't just copy the issue)
3. **Link to related issues** using `Closes #N` or `Related to #N`
4. **Highlight breaking changes** if any
5. **Describe testing performed**
6. **No AI attribution** anywhere in PR metadata

### Responding to Review Feedback

- **Respond promptly** to reviewer comments
- **Make requested changes** or explain why they're not appropriate
- **Push updates** as new commits (don't force-push during review)
- **Mark conversations resolved** after addressing feedback

## Authoritative Rules in .claude/

The **`.claude/` directory** contains authoritative operating rules:

### When to Reference .claude/

Before every task, check the relevant `.claude/` document:

- **Making any change**: Read `PRINCIPLES.md`
- **Creating commits**: Read `COMMITS.md`
- **Opening PRs**: Read `PULL_REQUESTS.md`
- **Writing tests**: Read `TESTING.md`
- **Security work**: Read `SECURITY.md`

### Hierarchy of Documentation

When documentation conflicts:

1. **`.claude/` rules** are authoritative
2. **`docs/` files** provide implementation guidance
3. **Code comments** explain specific decisions
4. **Git history** shows past reasoning

If you find contradictions:

- **Create an issue** to resolve the conflict
- **Do not guess** which source is correct
- **Ask for clarification** from maintainers

### Never Override .claude/ Rules

The following are **non-negotiable**:

- TypeScript strict mode settings
- Testing requirements
- Security validation rules
- Commit message format
- No AI attribution policy
- Issue-driven workflow
- Small, focused changes

If you believe a `.claude/` rule should change:

1. **Create an issue** proposing the change with reasoning
2. **Get maintainer approval** before proceeding
3. **Update documentation** as part of the change

## Common Pitfalls

### Pitfall: Scope Creep

❌ **Bad**:

```
Issue: "Fix ZIP extraction bug"
PR: "Fix ZIP bug, add TAR support, refactor security engine, update all deps"
```

✅ **Good**:

```
Issue: "Fix ZIP extraction bug"
PR: "Fix ZIP extraction bug"
Follow-up issues created for other improvements
```

### Pitfall: Weakening Safety

❌ **Bad**:

```typescript
// TypeScript complains about undefined, so let's use any
function process(entry: any) {
  return entry.name.toLowerCase();
}
```

✅ **Good**:

```typescript
function process(entry: ArchiveEntry): string {
  if (entry.name === undefined) {
    throw new Error('Entry name is required');
  }
  return entry.name.toLowerCase();
}
```

### Pitfall: Silent Failures

❌ **Bad**:

```typescript
try {
  await validateArchive(file);
} catch (error) {
  // User should handle this themselves
}
```

✅ **Good**:

```typescript
try {
  await validateArchive(file);
} catch (error) {
  if (error instanceof SecurityError) {
    showSecurityWarning(error);
  }
  throw error; // Propagate for caller to handle
}
```

### Pitfall: Missing Tests

❌ **Bad**:

```
"The existing tests should cover this change"
// Adds new feature without new tests
```

✅ **Good**:

```
"Adding tests for new TAR extraction feature"
test: add TAR extraction test fixtures
test: add TAR adapter unit tests
test: add E2E test for TAR file workflow
```

### Pitfall: Premature Abstraction

❌ **Bad**:

```typescript
// Abstract base class for potential future archive formats
// that don't exist yet
abstract class BaseArchiveAdapterFactoryProvider {
  abstract createFactoryForFormat(): AbstractArchiveFactory;
}
```

✅ **Good**:

```typescript
// Simple interface for current needs
interface ArchiveAdapter {
  inspect(): Promise<ArchiveMetadata>;
  extract(destination: string): Promise<void>;
}
```

## Agent-Specific Workflows

### Claude Code Users

When using Claude Code CLI:

1. **Read `.claude/` docs** before asking Claude to make changes
2. **Provide issue context** when requesting implementations
3. **Review generated code** before committing
4. **Run all checks** after Claude makes changes
5. **Remove any AI attribution** Claude might add
6. **Edit commit messages** to follow project standards

### GitHub Copilot Users

When using Copilot suggestions:

1. **Verify suggestions** match project coding standards
2. **Check TypeScript types** are strict and accurate
3. **Review error handling** is explicit, not silent
4. **Ensure tests exist** for suggested code
5. **Remove generic comments** Copilot generates

### Cursor Users

When using Cursor:

1. **Provide .claude/ context** to the editor
2. **Review multi-file changes** carefully
3. **Verify suggestions** follow project patterns
4. **Check generated tests** are meaningful
5. **Remove AI attribution** from commits
